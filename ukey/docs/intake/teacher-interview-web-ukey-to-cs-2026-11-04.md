# 网页 UKey 接入到 C/S 方案：老师访谈与资料收集清单

日期：2026-11-04。用途：用已有网页接入经验确定 C/S 候选路线、可复用能力和待验证缺口。

## 1. 本次交流的起点

已知：网页端已实现 UKey 接入；C/S 接入需要解决；不修改业务源码；主要对象是医院、政府等单位，但范围不限于这些行业；方案需要满足项目适用的商用密码要求。

未知：网页是否有前置网关、是否修改过业务登录代码、采用哪些本地组件、谁执行认证、UKey 型号及证书用途、C/S 已有尝试与具体卡点、可变更范围。前置网关是此前的猜测，不作为事实写进询问或后续方案。

第一轮建议收集 8 组核心信息：6 组围绕网页已有能力及项目目标，2 组补齐 C/S 对象与实施边界。这是访谈组织建议，不是要求老师当场回答所有技术参数。老师暂不掌握时，记录对应资料或技术联系人即可。

## 2. 可直接发送的询问消息

老师您好，我想先梳理已完成的网页 UKey 接入，判断哪些能力可以用于不修改源码的 C/S 系统。现在还不清楚网页的具体实现，也不能确定是否有前置网关。想请您帮忙确认以下事项：

1. 网页从插入 UKey 到进入业务系统，完整操作顺序是什么？会打开哪些程序、出现哪些证书选择或 PIN 窗口？
2. 网页接入当时用了哪些产品或自研组件，改动了哪些地方？例如业务登录代码、浏览器插件、本地服务、统一认证平台或外部代理；这些方式可能同时存在。有没有架构图、部署清单或相关说明？
3. 使用的 UKey、驱动或中间件分别是什么厂商和型号/版本？证书由谁签发，代表个人还是机构，主要用于登录认证还是业务签名？
4. 哪个组件验证证书和身份？是否有允许其他客户端使用的认证接口、SDK、示例或配套安全客户端？如果不清楚，能否提供产品文档或技术对接人？
5. UKey 认证后，原业务系统是否还要输入账号密码？证书身份如何对应实际业务账号，由谁建立登录会话和维护映射？已知是否还能从其他入口直接登录？
6. C/S 最终要达到什么效果：必须经过 UKey 才能访问、用 UKey 登录并关联业务账号，还是还包括业务数据签名、通信/存储保护等？有没有对应的改造方案、验收指标或相关评估范围说明？
7. C/S 之前具体尝试过什么？请选一套代表系统说明名称、版本、运行环境、连接的服务及已知接口；它与网页案例是否属于同一业务、是否共用账号或后端？目前卡在设备调用、身份认证、业务连接还是业务登录，有无报错、日志、演示记录或厂家意见？若尚未实施，也请说明目前判断困难的依据。
8. 在不改源码的前提下，允许调整哪些地方？例如安装终端组件、修改服务器地址配置、调整防火墙/路由策略、配置已有认证接口，或改变客户端运行位置。对共享终端换人、打印/读卡等外设、性能和业务连续性有哪些要求？

如果有现成资料，我可以先看资料，再把剩余问题集中请教。资料可提供脱敏版本。

## 3. 八组核心信息及其设计作用

| 编号 | 核心问题 | 第一轮最低需要取得的内容 | 对 C/S 方案的影响 |
| --- | --- | --- | --- |
| W1 | 一次网页登录实际怎样发生？ | 插 Key、打开入口、选择证书、输入 PIN、进入业务的顺序；已知失败现象；一份演示记录或步骤说明 | 识别可观察的接入入口，避免把本地组件窗口、浏览器能力或业务登录混为一体 |
| W2 | 哪些组件参与、当时改了什么？ | 组件名称、厂商/维护方、版本、安装与部署位置；业务源码是否曾修改；是否存在网关/代理/统一认证平台的实际证据 | 区分业务代码集成、浏览器/本地组件、认证平台和代理方案；方式可以组合，不能只按页面外观判断 |
| W3 | 用什么 Key 和凭据？ | UKey 厂商型号或可识别材料；驱动/中间件名称版本；证书签发方、身份类型和用途；可找到的接口说明 | 评估设备库、平台、位数及证书用途能否复用；同型号外壳或同名接口不能代替兼容验证 |
| W4 | 谁验证身份、有哪些受支持的集成能力？ | 证书/持钥证明验证组件、维护方；接口或 SDK 文档是否存在；是否明确支持原生客户端认证；可用测试方式或技术联系人 | 评估能否复用认证服务，还是需要配套接入产品；只有验签函数或一个成功返回值不等于完整的客户端认证机制 |
| W5 | 认证身份怎样进入原业务会话？ | 是否保留原账号密码；账号映射位置与维护方式；会话由谁建立；已知的退出、换人和旧入口行为 | 判断现网完成的是接入认证、业务登录还是两者；决定 C/S 是否另需账号/会话适配 |
| W6 | 目标、适用要求和完成依据是什么？ | 本次 C/S 的目标功能；现有密码应用方案、适用指标及评估范围的相关部分；已验证与未验证的能力 | 确定验证范围；防止把网页成功经验扩展为任意 C/S 的合规结论；明确登录接入之外的工作 |
| C1 | C/S 对象与已尝试卡点是什么？ | 一套代表客户端的名称、版本、运行系统；与网页案例是否共享业务、账号或后端；目标服务或直连数据库情况；已知协议/端口/接口；已有方案、到达阶段及失败证据 | 决定需要解决设备适配、认证协议、流量接入或业务账号问题；协议未知时保留待验证，不能凭 C/S 名称推断 |
| C2 | 允许怎样部署、运行上有什么约束？ | 终端安装与权限条件、可改配置、网络变更范围、原厂支持范围、测试条件；共享终端/外设/连续性要求 | 决定代理、隧道、已有接口或远程应用等候选是否可实施；约束不明时不能承诺通用免改接入 |

问 W2 时，让对方描述“当时实际做了什么”，再记录是否属于某类架构。不要直接问成“已有网关是哪一款”。

问 W4 时，关注认证流程和服务边界，不先要求老师提供所有密码函数参数。具体算法参数、摘要处理、签名编码及接口调用约定应由后续选定的产品协议与 SDK 文档确定。

问 W5 时，查看证书身份、人员身份、业务账号与会话的关联关系，不能只记录页面显示的姓名或客户端 IP。证书更新、补发与人员身份延续的规则在后续补充。

## 4. 优先争取的五类材料

| 材料 | 可接受的形式 | 要保留的信息 |
| --- | --- | --- |
| M1 架构与部署材料 | 架构图、部署清单、简要手绘图或经确认的流程说明 | 终端、本地组件、认证端、代理/网关（如有）、原业务端各自在哪里，哪些连线确实存在 |
| M2 产品、UKey 与终端组件材料 | 产品名称/版本、安装说明、驱动/中间件或接入组件安装包、SDK 文档 | 维护方、型号、版本、运行平台与接口支持范围；组件是不是必装，以及由谁安装 |
| M3 一次网页登录及账号衔接材料 | 步骤/演示记录、接口文档、官方示例、脱敏配置或一次成功调用记录 | 谁调用设备、谁验证、谁建立业务会话；输入输出的结构和会话关联机制；保留错误码，敏感值脱敏 |
| M4 一个 C/S 代表案例 | 客户端及原厂说明、目标服务清单、已尝试方案、错误日志、截图或厂家答复 | 测试对象、版本、操作步骤、预期/实际结果、失败阶段、已经排除的原因及其依据 |
| M5 目标与验收材料 | 需求、密码应用方案相关章节、适用指标及评估范围说明、测试验收记录 | 本项目需要实现哪些目标；已有材料覆盖哪些系统和部署；哪些结论尚无证据 |

这些是资料类别，不要求凑齐五个单独文件。没有现成文档时，经负责人员确认的记录有助于形成初步候选，但仍需后续验证。

## 5. 按回答选择追问，避免一次把所有问题抛给老师

| 获得的回答或现象 | 再追问什么 | 应寻找的证据 |
| --- | --- | --- |
| 网页通过本地组件使用 Key | 组件由谁提供？是浏览器专用，还是支持原生调用？有哪些调用限制与支持平台？ | 安装包、官方 SDK/接口说明、支持矩阵或官方示例 |
| 希望网页和 C/S 复用同一支 Key 或证书 | 两边是否信任相同 CA、接受相同证书用途？厂家接口与集成使用条件是否覆盖？用户与授权如何衔接？ | 证书使用条件、信任与账号配置、产品支持说明及测试结果 |
| 网页业务登录代码接入了认证 | 具体改在前端还是服务端？认证服务是否允许其他接入方使用？C/S 是否已有受支持的身份接口？ | 原厂集成说明及接口文档；不据此要求逆向用户业务程序 |
| 存在统一认证平台 | 支持哪些客户端接入方式？原 C/S 是否能接受其结果？账号、权限和会话如何衔接？ | 平台与业务双方的接口能力、会话或登录流程说明 |
| 确认存在前置网关/代理 | 是仅处理 Web，还是提供 TCP/IP 资源与配套客户端？支持哪种 Key 认证？ | 对应型号/版本的功能与配置说明；不要只按产品类别推断 |
| 网页登录成功，但业务仍要输入密码 | UKey 目前负责哪段身份鉴别？是否有原账号关联或访问强制措施？ | 需求边界、两段登录记录、已有账号关联或控制措施 |
| C/S 没有实际尝试 | 当前障碍判断来自产品限制、缺少源码、缺少接口，还是尚未研究？ | 厂家书面支持范围、既有需求和约束说明 |
| 识别不到 Key 或签名失败 | 独立厂家工具是否正常？失败在哪个调用？平台、位数和库路径是否匹配？ | 版本、调用错误、组件日志和厂家测试结果 |
| Key 认证通过，业务连接失败 | 哪个进程连哪个目标？有哪些协议/端口/动态依赖？原连接路径是否改变？ | 脱敏连接清单、配置、客户端与网关日志或已有记录 |
| 连接可用，但业务登录/身份关联失败 | 是否只完成通道认证？原业务接受什么登录方式？是否能切换为另一账号？ | 原厂接口说明、受控测试记录；账号映射表本身不足以证明强制关联 |
| 提出拔 Key 自动退出 | 需要撤销哪一层：新连接、隧道、原业务会话还是全部？未提交业务如何处理？ | 明确的目标、产品机制和测试结果 |

## 6. 信息如何转成候选方案

| 查明的条件 | 可以优先评估的方向 | 仍然不能省略的验证 |
| --- | --- | --- |
| 已有受支持的原生客户端证书认证，且能关联目标业务访问 | 复用设备支持和认证服务，验证 C/S 接入 | 原 C/S 如何使用身份结果、资源权限和业务账号关联 |
| 网关确实存在，且支持 Key 认证、相应协议资源和终端接入 | 配套安全客户端与网关配置试点 | 实际型号/版本、协议、权限、绕行和会话生命周期 |
| 网页直接集成 SDK/认证平台，缺少 C/S 接入 | 评估复用密码与身份服务，按目标业务补接入组件或适配 | 集成授权及接口支持，原 C/S 现有能力与不可修改边界 |
| 只有 Web 代理或网页状态能力 | 查明是否可扩展 C/S；评估独立的受控业务通道 | 认证到客户端通道的可靠关联、流量覆盖及原有校验兼容性 |
| C/S 是少量固定 TCP 服务，连接配置可调整或可受支持地引导 | TCP 代理或端口映射候选 | 端到端连接、业务协议、原有证书校验、账号与权限 |
| C/S 涉及 UDP、多端口或动态依赖，允许终端与网络变更 | 按业务资源限定的 IP 隧道或支持相应协议的产品候选 | 路由、DNS、回程、特殊发现机制、访问范围及业务兼容性 |
| 不能改源码，也没有现成身份接口或可实施的流量/登录适配 | 记录不能满足的具体目标；评估原厂配置扩展、受控运行等替代路线 | 替代方案的实际效果与适用指标；不能承诺安装 UKey 后全部满足 |

这些是基于条件的工程判断，不是对现网已存在某种产品或已具备某项功能的断言。原业务身份接口、代理、隧道和登录适配也可能组合使用。

## 7. 什么时候信息足够？

能够提出初步方案时，至少应当做到：

1. 能画出一次 Web 认证的功能链：谁调用 UKey、谁验证身份、谁建立原业务会话。尚未验证的连线明确标为假设。
2. 能识别主要产品、组件和责任方，掌握支持范围的资料或明确的补充路径。设备具体调用参数可在选定 SDK 后补齐。
3. 已选定一个 C/S 代表对象，知道现有登录、主要连接对象、已尝试卡点及允许的变更范围；协议等未知项有明确的验证安排。
4. 已区分本次目标是接入认证、业务账号身份关联、通信保护，还是还包括数据签名、存储等目标。

满足这些条件后，可以比较候选架构并制定试点，不等于已经能编写生产配置或作出完整合规结论。

进入实施验证前，再补充实际 SDK、测试 Key 与证书、认证和通道产品配置说明、原厂业务接口支持、测试环境、具体连接清单及相应变更条件。网页成功经验与第三方软件逆向结果都不能替代这些实证。

## 9. 资料依据与边界

[深信服官方 UKey 配置与排障说明](https://bbs.sangfor.com.cn/atrustdeveloper/aTrustClient/docs/8.%E5%B8%B8%E8%A7%81%E9%85%8D%E7%BD%AE%E7%B1%BB%E9%97%AE%E9%A2%98/8.1ukey%E8%AF%81%E4%B9%A6%E8%AE%A4%E8%AF%81%E9%85%8D%E7%BD%AE.html)分别涉及设备接口库、CA 匹配和客户端安装条件，说明只知道“支持 UKey”不足以确定具体集成方式。该厂商文档的支持限制不能扩大解释为所有产品的统一限制。

[《商用密码应用安全性评估管理办法》第十、十一条](https://oscca.gov.cn/sca/xxgk/2023-10/07/content_1061109.shtml)要求评估方案的适用指标、可实施性及所选技术、产品和服务，并对实际系统准确划定范围、根据客观凭据判定。本文据此询问方案和证据边界，不按“医院或政府单位”名称直接推断统一等级、指标或评估结论。
